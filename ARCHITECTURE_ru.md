## 1. Назначение и скоуп

CLI-менеджер секретов (паролей / API-ключей / заметок) с локальным зашифрованным
хранилищем. Без облака, без синхронизации, без сетевого стека.

**Явно вне скоупа:**
- Синхронизация между устройствами
- Browser-интеграция / автозаполнение
- Team-sharing секретов
- GUI

## 2. Threat model (явно)

Прежде чем говорить про AES и Argon2, нужно явно зафиксировать, от чего мы защищаем
и от чего — нет. Без этого раздела "security-проект" превращается в security theatre.

### Защищаем от:
- **Офлайн-атакующего с доступом к файлу `vault.enc`** (украденный ноутбук, бэкап,
  утечка из облачного синка папки). Без мастер-пароля файл должен быть
  computationally infeasible расшифровать.
- **Brute-force / dictionary атак на мастер-пароль** — за счёт memory-hard KDF
  (Argon2id), делающего перебор дорогим по железу.
- **Повреждения/усечения файла** — AEAD-тег обнаруживает и модификацию, и коррапт.
- **Concurrent-запись повреждающую vault** — atomic write + file lock
  `[grill-me v2: было заявлено, но не реализовано — см. §5 file lock]`.
- **Потерю данных при отключении питания в момент записи** — `fsync` перед
  `os.replace` `[grill-me v2, найдено OpenCode/F2, пропущено в v1]`.
- **Детекцию (не предотвращение) отката к старой версии vault-файла** — через
  monotonic revision-counter `[grill-me v2, см. §5]`.

### Явно НЕ защищаем от (вне скоупа, но фиксируем письменно):
- Кейлоггеров или malware на машине пользователя в момент ввода пароля.
- Memory dump / core dump в момент, когда vault разблокирован в текущем процессе.
- Root/administrator-доступа к работающей машине.
- **Zeroization ключа/пароля в памяти процесса.** `[grill-me v2: заменяет
  прежнюю формулировку про "mlock-подобные меры".]` CPython не даёт гарантий
  zeroization для `str`/`bytes` — значения иммутабельны, копируются GC,
  `cryptography` хранит собственные копии ключа в heap. Честная позиция: не
  защищаем, а не "частично митигируем" incorrect claim'ом, который ничего не
  выполняет на практике.
- **Предотвращение rollback-атаки** (см. выше — детектируем, не предотвращаем;
  полное предотвращение требует внешнего доверенного состояния вне файла,
  что вне скоупа для локального CLI без сервера).
- Multi-user shared-machine сценариев (permissions на файл — best effort через
  `0600` на POSIX; **на Windows это no-op** `[grill-me v2]` — ACL не
  выставляется, задокументировать как known limitation в `--help`).
- Clipboard sniffing другим процессом, `ps`/shell-history утечка `<title>` как
  метаданных, shoulder surfing при `--print` `[grill-me v2, TM-5]` —
  митигируется частично (autoclear буфера, см. §8), но не исключается
  полностью; фиксируем явно, а не оставляем недосказанным.

Это не отговорка "не будем делать нормально" — это стандартная практика: без
явного threat model нельзя обоснованно выбирать между "усложнить X" и "не
усложнять X".

## 3. Ключевое архитектурное решение: используем аудированные примитивы

Крипто-примитивы (AES-GCM, Argon2id) реализуются **не самостоятельно**, а через:

- [`cryptography`](https://cryptography.io/) (pyca) — AES-256-GCM, constant-time
  сравнения, CSPRNG
- [`argon2-cffi`](https://argon2-cffi.readthedocs.io/) — bindings к reference C
  implementation Argon2

**Почему не "с нуля", как в остальных портфолио-проектах:** в `autograd-engine`
цель — понять, что происходит "под капотом" у PyTorch, и ошибка в реализации
максимум даёт неверный градиент, который тесты сразу поймают. В крипто-примитиве
ошибка (неконстантное время сравнения, переиспользование nonce, некорректный
padding) — это **тихая уязвимость**, которая не проявится ни в одном юнит-тесте,
но полностью ломает security-гарантию. Собственная реализация AES здесь была бы
демонстрацией не мастерства, а непонимания области.

То, что "с нуля" в этом проекте — это: формат хранилища, схема vault'а, CLI,
key-derivation pipeline, atomic-write логика, session/timeout handling. Это
достаточно инженерной работы, чтобы проект был содержательным.

```

├── __init__.py
├── cli.py              # Typer app, команды, Rich-вывод

├── storage.py          # Бинарный формат файла, atomic write, backup
├── models.py            # Pydantic v2: VaultEntry, VaultMetadata, VaultConfig
├── generator.py        # Криптостойкая генерация паролей (модуль `secrets`)
├── clipboard.py        # Копирование в буфер с авто-очисткой
├── clipboard_clearer.py # Detached helper: очистка буфера по таймеру [grill-me v3]

```

Зависимость направлена сверху вниз: `cli.py → vault.py → {crypto.py, storage.py,
generator.py, clipboard.py} → models.py`. `crypto.py` и `storage.py` не знают
друг о друге — `vault.py` их оркестрирует.

## 5. Формат хранилища

Один бинарный файл (по умолчанию `~/.secure_vault/vault.enc`).

```
Offset  Size    Поле
0       4       magic bytes b"SSV\x00"
4       1       format version (uint8) = 1
5       1       kdf_type (uint8) — 0x01 = Argon2id (протокольная константа,
                не конфигурируется; фиксирует argon2-cffi hash type)
6       16      salt (Argon2id, os.urandom(16), см. lifecycle ниже)
22      1       argon2_time_cost (uint8, допустимый диапазон см. §6)
23      4       argon2_memory_cost_kib (uint32, big-endian, допустимый диапазон см. §6)
27      1       argon2_parallelism (uint8, допустимый диапазон см. §6)
28      1       argon2_hash_len (uint8) = 32 (протокольная константа)
29      8       revision_counter (uint64, big-endian, монотонно возрастает
                при каждом успешном write) [grill-me v2, детекция rollback]
37      12      AES-GCM nonce (os.urandom(12), lifecycle см. ниже)
49      N       ciphertext || GCM tag (tag = 16 байт, встроен в конец
                cryptography-вывода)
```

`[grill-me v2]` Добавлены `kdf_type`, `argon2_hash_len`, `revision_counter`
по итогам обоих независимых прогонов `grill-me` — в v1 их отсутствие означало,
что при смене дефолтов `argon2-cffi` расшифровка старых vault'ов могла сломаться
без пути миграции, а отката файла к старой версии нельзя было обнаружить.

**Порядок валидации заголовка** `[grill-me v3, OpenCode V2-NEW-9]`: строго
`magic → version → kdf_type → диапазоны KDF-параметров`, с ранним возвратом
на первом несовпадении. Экспортный формат (magic `b"SSVE"`, см. §10) должен
быть отклонён на первом шаге как "not a vault file", не провалиться дальше
как "bad version" — magic проверяется целиком (4 байта), а не как префикс.

### AAD — точное определение `[grill-me v2, было CRITICAL у обоих агентов]`

**AAD = raw-байты заголовка `[0:37)` (offset 0 включительно до offset 37
исключительно).** Операционное правило: `encrypt` сериализует заголовок один
раз в буфер байт — тот же буфер одновременно пишется на диск как заголовок
файла и передаётся в AES-GCM как AAD. `decrypt` берёт этот диапазон как
**slice уже прочитанных с диска байтов**, никогда не реконструируя его
заново из распарсенных Pydantic-полей `[grill-me v3: переформулировано по
F19 — прежняя редакция провоцировала implementer'а искать общий объект
между encrypt/decrypt вместо простого byte-slice]`. Любой bug в
canonicalization (порядок полей, endianness) при пересборке тихо снимает
защиту от подмены KDF-параметров — именно поэтому пересборки быть не должно
вообще.

Обязательные тесты: flip 1 бит в любом байте `[0:37)` → `decrypt` кидает
исключение; отдельно — flip байта в nonce `[37:49)` → тоже исключение
(регрессионный тест на случай, если кто-то «оптимизирует» передачу nonce
через отдельный путь) `[grill-me v3, Claude Code F25]`.

### Salt / Argon2 / nonce — жизненный цикл `[grill-me v2, зафиксировано с пользователем]`

- **Salt** генерируется один раз — при `vault init` — и живёт всё время
  существования vault'а. Перегенерируется **только** при
  `change-master-password` (см. §8).
- **Argon2id прогоняется один раз за вызов CLI** (один invocation процесса =
  один KDF-вызов → производный ключ используется для всех операций
  шифрования/дешифрования в рамках этого вызова).
- **Nonce — свежий `os.urandom(12)` на каждый отдельный вызов AES-GCM
  encrypt**, то есть на каждую операцию записи файла, а не на каждый
  entry внутри vault'а (весь `VaultMetadata` шифруется одним blob'ом за один
  `encrypt`-вызов). Ключ переиспользуется между записями (salt фиксирован →
  KDF не гоняется повторно) — единственная защита от `(key, nonce)`-реюза в
  GCM — это случайность nonce на каждый вызов. Birthday bound для 96-бит
  nonce: при `w` записях риск коллизии ≈ `w² / 2⁹⁷` — пренебрежимо для
  личного vault'а (даже при `10⁶` записей риск на уровне `10⁻²⁰`).

### Revision counter — детекция rollback `[grill-me v3: sidecar переписан по итогам гонки, найденной OpenCode]`

`revision_counter` инкрементируется на 1 при каждой успешной записи и входит
в AAD (защищён тегом от подмены без знания пароля). Детектирует, но **не
предотвращает** откат файла к старой валидной версии.

**Sidecar-файл** — `<vault_path>.rev` (per-vault, деривируется от пути
vault'а, а не хардкод `~/.secure_vault/.last_revision` — иначе несколько
vault'ов через `--vault-path` делят один счётчик и генерируют ложные
warning'и `[grill-me v3, найдено обоими агентами]`). Содержит только число
(plaintext, не секрет).

**Запись sidecar — часть той же критической секции, что и запись vault'а**,
не отдельная операция после unlock: gонка возможна именно потому, что в v2
sidecar читался/писался вне lock'а — два параллельных `add` могли оба
прочитать revision=5, оба инкрементировать до 6, и второй тихо перезаписывал
sidecar тем же значением 6 вместо 7, ломая саму детекцию `[grill-me v3,
OpenCode V2-NEW-1]`. Актуальный порядок (см. Atomic write ниже) держит lock
на всём цикле: чтение vault + чтение sidecar + запись vault + fsync + запись
sidecar + fsync — единая атомарная секция.

**Честная граница механизма** `[grill-me v3, OpenCode V2-NEW-2]`: sidecar —
plaintext-файл без собственной защиты целостности, лежащий рядом с vault'ом.
Атакующий, имеющий право записи в директорию (то есть уже способный
подменить `vault.enc` — ровно тот сценарий, что и rollback), может откатить
и `.rev` вместе с vault'ом, обнулив детекцию. Это **не баг конкретной
реализации, а фундаментальное ограничение** любой sidecar-схемы без внешнего
доверенного состояния: механизм ловит **точечный** откат одного файла (баг
синка, ручная ошибка), но не системный rollback всей директории атакующим,
которому уже принадлежит эта директория. Отсутствие `.rev` при первом
запуске трактуется как `revision=0` (не ошибка).

**Обработка битого `.rev` и crash-gap** `[grill-me v4, добивка V2-NEW-1]`:
`.rev` содержит только десятичное ASCII-число. При ошибке парсинга
(не-число, пусто, вне `0..2⁶⁴-1`) файл трактуется как `0` с предупреждением
в stderr, а не как фатальная ошибка — иначе атакующий может DoS'ить
запись, подложив мусор в sidecar. Коррапт `.rev` никогда не блокирует
операцию записи. После краша между шагом 7 (`os.replace` vault) и шагом 9
(запись `.rev`) следующий успешный write вычислит
`max(header_rev, sidecar_rev)+1`, что даёт gap на 1 (например `6->8`). Gap
задокументирован как ожидаемый и не считается багом — инвариант
"revision строго монотонна", а не "revision +=1 без пропусков".

### Atomic write `[grill-me v4: добит finally и Windows-handle у писателя; база — v3 lock расширен на sidecar]`

1. Открыть/создать `<vault_path>.lock` и взять advisory file lock
   (`fcntl.flock(LOCK_EX)` на POSIX; `msvcrt.locking(LK_LOCK)` в цикле с
   ретраями на Windows) — **с таймаутом** (по умолчанию 10 секунд). При
   истечении таймаута — не сырой traceback, а структурная ошибка
   `VaultBusyError("another operation in progress")` `[grill-me v3, оба
   агента отметили Windows-семантику без таймаута как дефект]`. Lock
   держится на **весь** цикл ниже, включая шаги с sidecar — это и есть фикс
   гонки из предыдущего пункта. **Весь цикл 2–9 выполняется в `try/finally`,
   шаг 10 — в `finally`** `[grill-me v4, добивка V2-NEW-1: без finally любой
   early-return/исключение между шагами 3 и 9 оставлял бы lock висящим до
   таймаута]` — при ошибке на любом шаге до 7 sidecar не пишется вовсе,
   lock всё равно освобождается.
2. Прочитать `vault.enc` целиком в память и **закрыть file handle до вызова
   `decrypt`** — правило действует и для читателей (`get`/`list`), и для
   писателей (`add`/`update`/`delete`/`import`) `[grill-me v4, расширение
   v3 F18: в v3 писатели были исключены, на Windows их открытый handle так
   же блокирует `os.replace` параллельного писателя]`. Argon2id занимает
   большую часть времени операции — держать handle открытым все эти секунды
   создаёт на Windows риск: `os.replace` падает с `PermissionError`, потому
   что Windows не открывает файлы с `FILE_SHARE_DELETE` по умолчанию
   `[grill-me v3, Claude Code F18]`. Писатель дополнительно оборачивает шаг 6
   в retry-with-backoff (3 попытки, экспоненциальная пауза) на случай
   `PermissionError` от параллельного читателя.
3. Расшифровать `vault.enc` (валидация заголовка `magic→version→kdf_type→
   диапазоны до KDF, см. §6). Прочитать `<vault_path>.rev` (или считать `0`,
   если файла нет; битый `.rev` → `0` с warning, см. выше).
4. Скопировать текущий `vault.enc` → `vault.enc.bak` (best-effort).
5. Сериализовать → зашифровать (новый nonce, `revision_counter = max(header
   revision, sidecar revision) + 1` — берём максимум на случай рассинхрона)
   → записать в `vault.enc.tmp`.
6. `f.flush()` + `os.fsync(f.fileno())` на `vault.enc.tmp` **до** rename.
7. `os.replace("vault.enc.tmp", "vault.enc")`.
8. На POSIX — `os.fsync()` на fd родительской директории после rename.
9. **Записать `<vault_path>.rev` строго после успешного шага 8**, не до
   `[grill-me v3, OpenCode V2-NEW-1: запись до replace даёт ложный alarm
   навсегда при крахе между шагами]`, через тот же tmp+fsync+replace паттерн
   (файл маленький, но принцип тот же — не оставлять частично записанный
   счётчик). Если шаги 5–8 не завершились успешно, шаг 9 не выполняется.
10. Освободить lock (в `finally`).

**Backup policy**: глубина хранения — одно поколение (`vault.enc.bak`
перезаписывается каждым сохранением). Восстановление — ручное: `cp
vault.enc.bak vault.enc`, задокументировать в `--help`/README.

**Расшифрованный plaintext** — JSON-сериализация `VaultMetadata` (Pydantic v2):

```python
class VaultEntry(BaseModel):
    id: UUID
    title: str
    username: str | None = None
    secret: str
    notes: str | None = None
    tags: list[str] = []
    created_at: datetime
    updated_at: datetime

class VaultMetadata(BaseModel):
    schema_version: int = 1

```

## 6. KDF и шифрование — параметры

```python
class KDFConfig(BaseModel):
    time_cost: int = 3              # допустимый диапазон при чтении: 2..10
    memory_cost_kib: int = 65536    # 64 MiB; допустимый диапазон: 19456..262144 (19..256 MiB)
    parallelism: int = 4            # допустимый диапазон: 1..8
    hash_len: int = 32              # протокольная константа, -> 256-bit ключ для AES-256
    salt_len: int = 16
```

Значения по умолчанию — отправная точка из OWASP Password Storage Cheat Sheet
для Argon2id, конфигурируемые при `vault init --time-cost N --memory-cost N
--parallelism N` (все три флага, не только первые два — `[grill-me v3, Claude
Code F20: в v2 `--parallelism` был конфигурируем в файле, но не имел CLI-флага]`).

**Верхняя граница понижена с 1 GiB до 256 MiB** `[grill-me v3, OpenCode
V2-NEW-6]`: 1 GiB — внутри технически допустимого диапазона, но легитимный
(не атакующий) вызов с `memory_cost=1 GiB` убивает процесс на CI-раннере или
контейнере с 512 MiB лимитом ровно так же, как атака — `OOM killer` без
структурной ошибки, просто падение. 256 MiB — достаточно щедрый предел для
Argon2id (значительно выше OWASP-минимума) и безопасен на типичных
constrained-окружениях.

**Верхняя граница обязательна** `[grill-me v2, CRYPTO-2, HIGH]`: формат файла
хранит `memory_cost_kib` как `uint32`, что допускает значения вплоть до ~4 GiB.
Атакующий с правом записи в файл может подставить экстремальные
KDF-параметры — жертва при попытке разблокировать vault получит OOM/kill
процесса. `storage.py` **обязан** валидировать диапазон параметров при чтении
заголовка **до** вызова Argon2id и отклонять файл с понятной ошибкой, если
значения вне диапазона выше.

**Верификация мастер-пароля** — НЕ через отдельный password hash. Единственная
проверка — попытка AES-GCM decrypt и сверка тега.

### Классификация ошибок при открытии vault'а `[grill-me v2, уточнение]`

Различаем два класса, а не один:

1. **Структурные ошибки** (bad magic, неизвестная `version`, файл короче 49
   байт, KDF-параметры вне допустимого диапазона) — детектируются **до**
   попытки расшифровки и ничего не раскрывают о пароле. Их можно и нужно
   сообщать точно ("unsupported vault format" / "corrupted header"), **но не
   с точностью до конкретного нарушенного байта/поля** `[grill-me v3,
   OpenCode V2-NEW-5]`: отличие "bad magic" от "bad kdf_type" по-прежнему
   ничего не даёт офлайн-переборщику пароля (у него уже есть сам файл со
   всеми параметрами в заголовке), но детальное сообщение может помочь
   атакующему, **готовящему** malformed vault для атаки на CLI жертвы,
   отличать поддельные заголовки от настоящих без обращения к самому CLI.
   Сообщение — одно на весь структурный класс: "vault file is invalid or
   unsupported".
2. **Крипто-ошибки** (неверный GCM-тег после успешного парсинга заголовка) —
   здесь единое сообщение `"Decryption failed: wrong password or corrupted
   vault"` и **единый exit code** для обоих случаев (wrong password vs
   corrupted ciphertext) — иначе разный exit code сам становится oracle,
   обходимым скриптом даже при одинаковом тексте сообщения.

### Минимальная проверка мастер-пароля `[grill-me v2, TM-3, HIGH; уточнено v3]`

Вся гарантия "computationally infeasible" в §2 держится на предположении, что
brute-force дорог из-за Argon2id — но это верно только относительно случайного
или достаточно энтропийного пароля. При `vault init` и `change-master-password`
выполняется базовая проверка силы пароля (минимальная длина ≥ 12 символов +
проверка по **встроенному статическому списку** самых частых утёкших паролей
— **без сетевых запросов** `[grill-me v3, Claude Code F20: устраняет
противоречие со скоупом §1 "без сетевого стека" — формулировка в v2 была
неоднозначна и допускала прочтение как HIBP-подобный live lookup]`; список —
несколько тысяч записей, зашитых в пакет, без zxcvbn). Проверка **не
блокирует** жёстко (`--i-know-its-weak` для явного подтверждения).

**Та же проверка применяется к export-паролю** при `vault export`
`[grill-me v3, Claude Code F20]` — он защищает те же секреты офлайн, что и
мастер-пароль, и в v2 был пропущен из этой политики без обоснования.

## 7. Session model: **stateless**

Каждый вызов CLI, требующий доступа к секретам (`get`, `add`, `list`, `export`,
...), запрашивает мастер-пароль заново через `getpass` (не отображается, не
попадает в shell history).

**Почему не daemon/unlock-session с TTL:** это самый безопасный дефолт — ключ
живёт в памяти процесса ровно на время одной операции, а не потенциально часами
в фоновом демоне. Для портфолио-проекта это также architecturally проще и не
создаёт лишней поверхности атаки (unix socket демона, PID-файл, race conditions
при параллельных вызовах).

Явно фиксирую как *возможное будущее расширение*, не для v1: `vault unlock
--timeout 300` с ключом, закешированным в памяти отдельного background-процесса.
Если захочешь — обсудим отдельно, это отдельный architectural surface с
собственным threat model.

## 8. CLI-команды (Typer)

```
vault init                          # создать новый vault, задать мастер-пароль
vault add <title>                   # добавить запись (интерактивный prompt на secret)
vault get <title>                   # показать / скопировать в буфер
vault list [--tag TAG]              # список записей (без секретов)
vault update <title>                # изменить запись
vault delete <title>                # удалить запись
vault generate [--length N]         # сгенерировать пароль (не требует unlock)
vault change-master-password        # re-encrypt с новым паролем, новый salt
vault export --out FILE             # зашифрованный экспорт (новый пароль обязателен)
vault import --in FILE              # импорт из зашифрованного экспорта
vault status                        # revision, кол-во записей, путь к .bak
```

### `generate` — криптостойкий генератор

`generator.py` использует модуль `secrets` (не `random`). Конфигурируемые: длина,
наборы символов, минимальное число цифр/спецсимволов. Не требует unlock vault'а —
чистая функция без побочных эффектов.

### `get` — clipboard с авто-очисткой через detached helper-процесс

`[grill-me v2, было CRITICAL у обоих независимых агентов]` В v1 предполагался
`threading.Timer` внутри процесса `vault get` — архитектурно нерабочая схема:
CLI-процесс завершается сразу после вывода (обычный UX для однократной
команды), поток-таймер умирает вместе с родителем, буфер физически никогда не
очищается. Ждать таймер в foreground (non-daemon) означало бы блокировать
команду на 20 секунд — неприемлемый UX для CLI-утилиты.

**Решение:** `clipboard.py` копирует секрет через `pyperclip` и запускает
**отдельный detached процесс** `clipboard_clearer.py`, который спит заданное
время, затем очищает буфер **только если он всё ещё содержит именно этот
секрет** (сверка через `hmac.compare_digest`, не `==`, — та же дисциплина
constant-time сравнения, что и для GCM-тегов в §12 `[grill-me v3, OpenCode
V2-NEW-4]`).

Хэш секрета передаётся helper-процессу **через временный файл в
`tempfile.mkstemp()`**, путь к которому передаётся аргументом, **не сам хэш
через `--hash`** `[grill-me v3, OpenCode V2-NEW-4, значимая находка второго
раунда]`: аргументы процесса видны в `ps aux` **всем локальным пользователям**
на всё время жизни таймера (по умолчанию 20 секунд) — хэш секрета в `argv`
превращается в offline dictionary-oracle, доступный любому, кто может
выполнить `ps` в момент работы таймера, даже без соли на хэше. Временный файл
создаётся с `0600` на POSIX; на Windows `0600` — no-op (см. §2, ACL не
выставляется) `[grill-me v4, добивка V2-NEW-4]` — поэтому файл живёт
минимальное окно и удаляется helper'ом сразу после чтения в `finally`; на
Windows дополнительно — best-effort `SetFileInformationByHandle` / ACL через
`win32security` если доступно, иначе задокументировать как known limitation
(хэш в файле доступен любому локальному пользователю, успевшему прочитать
его по пути из `argv` за ~20 сек).

Жизненный цикл файла `[grill-me v4]`: родитель `mkstemp → write(hash) →
os.fchmod(0o600) → close(fd) → Popen →` helper `read → unlink` в `finally`.
Если `Popen` кидает исключение или недоступен — **родитель удаляет файл
сам в своём `finally`** (иначе хэш остаётся на диске неопределённо) и
переходит к graceful degradation: предупреждение в stderr, что autoclear не
сработает, без падения основной команды. Путь к файлу всё ещё виден в
`argv` helper'а (`--hash-file <path>`), но это не offline-oracle: путь
рандомен (`mkstemp` + `O_EXCL`), без чтения файла по этому пути атакующий
ничего не получает; чтение защищено `0600` на POSIX.

Запуск: `subprocess.Popen([sys.executable, "-m",
"secure_secrets_vault.clipboard_clearer", "--hash-file", tmp_path, "--delay",
"20"], start_new_session=True)` на POSIX; на Windows —
`creationflags=subprocess.DETACHED_PROCESS |
subprocess.CREATE_NEW_PROCESS_GROUP` вместо `start_new_session`, которое
действует только на POSIX и на Windows было бы no-op `[grill-me v3, оба
агента отметили Windows-специфику отдельно]`.

`pyperclip` на Linux требует системный `xclip` или `xsel` — задокументировать
как runtime-зависимость в README (`[grill-me v2, портативность]`).

Также доступен флаг `--print` для явного вывода в stdout вместо буфера (для
скриптования, на свой риск — без autoclear).

## 10. Export / Import

- Экспорт **всегда** зашифрован заново с **новым** `salt` и `nonce`
  `[grill-me v2, EXP-3: явно, независимо от того, совпадает ли export-пароль с
  основным — иначе ключ экспорта совпадёт с ключом рабочего vault'а]`, с
  отдельным паролем (может быть тем же, может — другим, для передачи третьей
  стороне, double-prompt при вводе). Формат идентичен основному vault-файлу
  (magic bytes другие: `b"SSVE"` — export, чтобы не спутать с рабочим vault
  случайно). `revision_counter` в экспорте начинается с 0 (это новый,
  независимый файл, не продолжение истории рабочего vault'а). Запись экспорта
  идёт через тот же atomic-write путь (§5), включая `fsync` — прерванный
  экспорт не должен оставлять частично записанный файл.

- **Import — merge-семантика** `[grill-me v2, было CRITICAL у Claude Code]`:
  - Импорт по умолчанию требует уже инициализированного vault'а; флаг
    `--init-if-missing` позволяет создать новый vault прямо в процессе
    импорта (с запросом нового мастер-пароля), если `vault.enc` отсутствует
    — иначе восстановление после потери файла требует отдельного танца
    `init` → сразу `import`, что легко забыть в стрессовой ситуации
    восстановления `[grill-me v3, OpenCode V2-NEW-8]`.
  - При коллизии `id` (UUID) — запись пропускается, в вывод CLI — предупреждение
    со списком пропущенных `id`. UUID уникален по конструкции, коллизия почти
    всегда означает "эта запись уже была импортирована ранее" — молчаливый
    overwrite здесь означал бы возможность тихо затереть существующий секрет
    данными из недоверенного экспорта.
  - При коллизии `title` (разные `id`, одинаковый `title`) — запись **всё
    равно импортируется** (title не уникальный ключ), но CLI выводит
    предупреждение о неоднозначности для последующего `vault get <title>`
    (см. §13, "дубли title" — резолвится по последнему добавленному,
    пользователь может переименовать вручную).
  - Флаг `--overwrite-conflicts` (переименован из `--force` в v2 —
    см. ниже про коллизию имени флага) заменяет "skip on id collision" на
    "overwrite" — только явный, не дефолтный путь.
  - **`revision_counter` инкрементируется даже если все записи были
    пропущены** (import с нулевым эффектом на данные) `[grill-me v3, OpenCode
    V2-NEW-8]` — это осознанный компромисс: инвариант "revision == число
    операций записи файла", а не "revision == число фактических изменений
    данных". Строгий второй инвариант потребовал бы отменять запись файла
    целиком при no-op import, что усложняет atomic-write путь без реальной
    пользы — задокументировано, не считается багом.

- Plaintext-экспорт НЕ является дефолтным путём. Доступен только через явный
  флаг `--unsafe-plaintext-json FILE` — канал явно фиксирован как **файл**, не
  stdout (stdout попадает в shell scrollback/CI-логи бесконтрольно; файл хотя
  бы можно поставить в `0600` и явно удалить). На интерактивном терминале
  (`isatty() == True`) требует подтверждения `y/N`. **На неинтерактивном
  пути (пайп/CI) требуются оба фактора одновременно: флаг `--yes-i-understand`
  И символ `y`, прочитанный из stdin** — не один вместо другого
  `[grill-me v3, OpenCode V2-NEW-7, значимая находка: имя флага `--force`
  совпадало у import (=overwrite) и export (=non-tty bypass), и при
  реализации "не-tty → --force" вместо "не-tty → --force И y" `echo y | vault
  export --unsafe... --force` превращался в задокументированный обход
  интерактивного подтверждения, то есть ровно то, что подтверждение должно
  было предотвращать]`. Флаг переименован в `--yes-i-understand`, чтобы не
  делить имя с `--overwrite-conflicts` у import — разные последствия не
  должны прятаться за одним токеном `--force`.

  После записи — предупреждение в stderr с точным путём файла и напоминанием
  удалить его после использования. JSON без MAC — модификация файла перед
  повторным `import` не обнаруживается; для unsafe-режима это принятый
  компромисс, фиксируем письменно. **Plaintext-import (обратная операция —
  чтение unsafe-экспорта обратно в vault) вне скоупа v1** `[grill-me v3,
  Claude Code F21: в v2 текст ссылался на "повторный import" plaintext-файла,
  хотя такой команды не существует — `vault import` принимает только
  зашифрованный `SSVE`-формат; если plaintext-import появится в будущем, он
  станет ровно тем вектором обхода merge-защиты, который описан выше для
  `--overwrite-conflicts`, и должен получить собственный grill-me-раунд, а не
  наследовать эту спецификацию по умолчанию]`.

## 11. Обработка ошибок и логирование

- **Секрет/пароль никогда не попадает в исключения, traceback или логи.**
  Кастомные exception-классы (`exceptions.py`) различают структурный класс
  (`CorruptedVaultError`, `UnsupportedFormatError`) и крипто-класс
  (`AuthenticationFailedError` — единое сообщение и единый exit code, см. §6)
  — никогда не несут значения полей вроде секрета или пароля.
- Логирование операций ("vault unlocked", "entry added") — на уровне
  операции; включать ли `<title>` в лог — осознанное решение, а не default:
  title — метаданные о структуре vault'а, для строгого режима можно логировать
  только `id` `[grill-me v2, F14]`.
- **`<title>` как позиционный аргумент CLI** (`vault get <title>`) виден в
  `ps aux`, shell history, `auditd` на время выполнения команды
  `[grill-me v2, SESS-4, known limitation, LOW]`. Задокументировать в
  `--help`; альтернатива (запрос title через интерактивный prompt вместо
  argv) — не берём в v1, ухудшает скриптуемость сильнее, чем оправдывает риск
  для локального однопользовательского CLI.
- Дубли `title` при `add`: не запрещаем (title — не уникальный ключ, `id` —
  уникальный), но `get`/`update`/`delete <title>` при нескольких совпадениях
  резолвятся по последней добавленной записи с явным предупреждением в CLI о
  неоднозначности `[grill-me v2, F13]`.
- `mypy --strict` обязателен, как и в остальных проектах; `Pydantic v2` — для
  всех схем.

## 12. Тестирование

Стандартный протокол проекта: реальный `pytest -v`, без фабрикации вывода.
Дополнительно к обычным unit/integration тестам — специфичный для крипто-модуля
чек-лист:

- Nonce **никогда** не повторяется между вызовами шифрования (property-test с
  детерминированным mock `os.urandom`, не голый random — иначе тест флакует
  `[grill-me v2, уточнение]`)
- Изменение любого байта в ciphertext или AAD `[0:37)` → `decrypt` кидает
  исключение, не возвращает мусорные данные (см. §5, точное определение AAD)
- Constant-time поведение сравнения тегов — полагаемся на `cryptography`
  (сама либа даёт эту гарантию), тест проверяет, что мы не добавили собственное
  `==` поверх байт секрета нигде в коде
- Wrong-password path и corrupted-ciphertext path дают **идентичное** сообщение
  **и идентичный exit code** (регрессия против oracle-утечки; structural errors
  — отдельный класс, см. §6)
- `vault.enc.tmp` не остаётся на диске после успешной операции
- **`fsync` вызывается** перед `os.replace` (мокается на уровне теста,
  проверяется факт вызова, а не реальный power-loss) `[grill-me v2]`
- **File lock** блокирует второй параллельный `add`/`update`/`delete`, пока
  первый не завершится — тест на два конкурентных вызова, не должно быть
  lost update `[grill-me v2]`
- **Sidecar `.rev` обновляется строго после `os.replace`** и находится под
  тем же lock'ом, что и запись vault'а — тест на два параллельных `add`
  проверяет итоговый `revision_counter == 2` (не `1` из-за гонки)
  `[grill-me v3]`
- **Lock-таймаут** отдаёт `VaultBusyError`, а не сырое исключение, при
  занятом lock'е дольше настроенного предела `[grill-me v3]`
- KDF-параметры вне допустимого диапазона **19456..262144 KiB**
  (обновлённая верхняя граница) при чтении заголовка →
  `UnsupportedFormatError` до вызова Argon2id, не OOM `[grill-me v3: диапазон
  сужен]`
- `revision_counter` уменьшился между запусками (сверка с `.rev`) →
  предупреждение о возможном rollback, с явным указанием в тексте
  предупреждения, что механизм не защищает от полного отката директории
  `[grill-me v3]`
- **Читатель и писатель закрывают file handle до `decrypt`** — mock-тест
   проверяет порядок вызовов `read()` → `close()` → `Argon2id` для обоих
   путей, до, а не после, криптографической операции
   `[grill-me v4: расширение v3 Windows-регрессии на писателя]`
- **Lock освобождается в `finally` при early-return/исключении** — тест
   инжектит ошибку между шагами 3 и 5 и проверяет, что второй `add` не
   получает `VaultBusyError` навечно `[grill-me v4, добивка V2-NEW-1]`
- **Битый `.rev` → `0` с warning, не фатальная ошибка** — запись с мусором в
   `.rev` всё равно проходит `[grill-me v4]`
- **Clipboard clearer** получает хэш через файл, не через `argv` — тест
   проверяет, что `secret_hash` не встречается в списке аргументов
   запущенного `subprocess.Popen` `[grill-me v3, OpenCode V2-NEW-4]`
- **Родитель удаляет tempfile при `Popen`-фейле** — mock `Popen` side_effect
   → `tmp_path` не остаётся на диске `[grill-me v4, добивка V2-NEW-4]`

Четвёртый раунд `grill-me` (после v4-патча) — финальная верификация delta
v4 (finally для lock, битый `.rev`, writer-handle, tempfile-cleanup) перед
стартом `crypto.py`. Третий раунд (v3) закрыл V2-NEW-1/V2-NEW-4 и разведение
`--force`; v4 добивает остаточную неполноту спеки внутри уже закрытых зон.

## 13. Порядок реализации

1. `models.py` — Pydantic-схемы (без крипто, без I/O)
2. `crypto.py` — KDF + AEAD encrypt/decrypt, изолированно тестируется
3. `storage.py` — бинарный формат, atomic write, поверх `crypto.py`
4. `vault.py` — оркестрация (`VaultManager`)
5. `generator.py`, `clipboard.py` — независимые утилитарные модули
6. `cli.py` — Typer-обвязка поверх всего

`code-review` — обязателен после каждого модуля, как и в предыдущих проектах,
с усиленным фокусом на модулях 2–4.

## 14. Статус реализации и осознанные отклонения

v1 реализован (все модули из §13, 88 тестов проходят, `mypy --strict` чист).
Пост-имплементационное code-review модулей 2–4 дало находки, которые слегка
изменили спеку ниже. Фиксируются здесь, чтобы документ честно отражал, где
код и текст расходятся:

1. **Decrypt выполняется внутри lock'а** (`vault.py`, `_transform`). Первая
   реализация расшифровывала вне критической секции `update_vault` и
   собирала payload из устаревшего снимка — два параллельных `add` оба
   расшифровывали старое состояние, и второй тихо затирал первый (lost update
   с *корректным* revision). Чтение → парсинг → KDF → decrypt теперь
   происходят внутри `transform`, то есть под lock'ом. «Единая атомарная
   секция» из §5 теперь буквально верна.
2. **Решения о коллизиях import принимаются тоже внутри критической секции**
   (раньше `existing_ids` снимался до lock'а). Списки skipped-id и
   ambiguous-title заполняются transform'ом под lock'ом; лишний прогон KDF на
   финальный пересчёт title убран.
3. **`initialize` проверяет существование внутри критической секции.** Pre-check
   через `exists()` остался для дружелюбного быстрого фейла, но авторитетная
   проверка — под lock'ом по `ctx.current_raw`; закрыт race check-then-act
   между двумя конкурентными `init`.
4. **Экспорт пишет прямым atomic write, а не полным циклом vault'а**
   (отклонение от §10 «тот же atomic-write путь»). Прогон экспорта через
   `update_vault` создавал рядом с экспортом мусор `.rev`/`.lock`/`.bak` и
   оставлял `.bak` под старым экспортным паролем. Теперь экспорт делает
   tmp+fsync+replace напрямую: это новый независимый файл (§10 и говорит так),
   откатывать нечего. Также явно отказывает при попытке писать поверх живого
   vault'а.
5. **`change-master-password` наследует KDF-параметры из текущего заголовка**,
   а не сбрасывает на дефолты — иначе пользователь, выбравший при init
   `--time-cost/--memory-cost/--parallelism`, тихо терял их при смене пароля.
6. **`update_entry`/`delete_entry` кидают `EntryNotFoundError` при отсутствии
   id**, вместо молчаливой no-op мутации данных с ростом revision.
   Консистентно с семантикой `resolve_title`; кроме того, неудачная мутация
   больше не порождает запись файла.
7. **Rollback-warning реализован на записи**: если ревизия текущего заголовка
   старее sidecar-ревизии, каждый писатель выдаёт предупреждение в stderr с
   явным указанием, что полный откат директории не покрывается (закрыт
   последний открытый пункт чек-листа §12).
8. **Честный разрыв с §6:** встроенный список утёкших паролей сейчас ~100
   записей, не амбициозные «несколько тысяч». Структура принимает больший
   датасет без изменения API; маленький список считаем best-effort до замены.
9. **Честный разрыв с §7:** import выполняет до трёх прогонов Argon2id за
   вызов (расшифровка импорт-файла + transform своего vault'а), а не строго
   один. Корректность (decrypt-inside-lock, п.1) выбрана вместо идеала
   «один KDF»; дополнительная цена ограничена и только на пути import.
